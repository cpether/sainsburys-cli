### Response-cookie follow-up

Ordinary HTTP responses previously ignored Set-Cookie, while successful live read responses were observed replacing cached cookie values. That is a concrete source gap, not proof of the live 401 cause. The retained HTTP implementation now uses tough-cookie 6.0.2 for host-only/domain/path/Secure/expiry/prefix/public-suffix rules, Max-Age precedence, replacements and deletions. Managed cached requests serialize under the same profile lock as login/logout, reload the latest matching login generation and persist private cookie state before readback. Abort/deadline checks prevent queued requests from sending later, and a delayed response cannot cross logout or a newer login. No bearer/custom-token synthesis, automatic cached reauthentication or mutation retry was introduced.

The HTTP and auth agents independently reviewed the changes. Findings fixed include lost positive Max-Age expiry after serialization and an old in-memory response overwriting a replacement session. The outer basket signal tracker now distinguishes a queued unsent mutation from an actual unverified write; two real CLI signal regressions fail on the old tracker and pass with the fix. Twenty-three cookie regressions and a login-generation regression cover rotation/persistence/reload, scopes, TTL/deletion, concurrent processes, login/logout races, cancelled/late requests, private-save failure and no mutation replay. Typecheck, build, all 183 tests and dependency audit pass, with zero advisories. The new dependency was added through the lockfile after checking its current primary documentation and registry metadata.

Claude Opus 5.5 high independently passed all 183 tests and typecheck, reproduced serialized rotations/expiry and local lock contention with dummy state, checked dependency lockfile integrity and found no material blockers. The undocumented API can change, bot protection may reject replay, and the profile/context schemas may require adjustments after sanitized live observation. A plan is not an atomic retailer transaction. Price changes or a readback failure can leave verified or uncertain partial changes. Weighted fulfillment, substitutions and later website actions prevent a local estimate from guaranteeing the eventual payment amount. Existing catchweight is preserved; new catchweight choices stay on the website. Removal still requires a resolvable product and valid price; otherwise use the website.

No diagnostics are retained: screenshots, HAR capture and browser-page dumps were removed. Private opt-in diagnostic capture would need a separate redaction/retention implementation before introduction. No SMS/chat bridge is supported. There is no automatic reauthentication loop and no payment/amendment/booking execution code.

The approval digest binds plan contents to a review, but does not authenticate a human or isolate the agent. A same-user shell-capable agent can read session state or alter this code. Strong enforcement requires credentials in a separately isolated account/service and an allowlisted interface with an approval channel outside agent control. Local logout cannot revoke copied tokens.


## Resident browser and readback recovery

Continued live diagnosis recorded removal PUT 200, then basket GET 500 JSON, then profile GET 401. Add, idempotent repeated application and quantity update had passed in the same run. The website showed the restored empty basket. This identifies the first failed readback status without establishing why the retailer rejected the subsequent session. Status-only instrumentation stayed outside the repository and did not log response bodies, cookie names/values, authentication headers or tokens.

Headless profile reuse encountered a browser challenge; headed minimized reuse reached sign-in even with cached cookies restored. The next implementation therefore keeps the dedicated headed Chromium process alive after explicit login. API requests execute inside its retailer page. Existing API modules, request shapes, response schemas, target-plan authorization and constraints remain. Normal commands reuse the same private local service, and only explicit `auth login` displays manual sign-in/MFA. The browser can renew an accepted website session, but cannot bypass fresh retailer MFA.

The local service uses a private Unix socket and atomic owner metadata, account/session-generation binding, bounded JSON frames and serialized work. It retains the profile lock until shutdown; logout stops it before clearing state. Credentials stay in the service and private cache. The renderer restricts exact HTTPS origin, paths, methods and redirects; strips caller credential/override headers; validates basket quantities/units/IDs before network; and verifies identity and amendment state again before every write. Cancellation reaches queued work and active fetches. A fresh dispatch acknowledgement plus absolute deadlines prevent a cancelled queued request from starting later. The same-user shell trust boundary is unchanged.

A specified transient post-write failure can cause one more basket GET after a 250 ms abortable delay. It never resends the mutation. Readback schema/mismatch/auth/deadline errors stay distinct and fail closed. Browser-backed reads have a bounded silent website recovery after authentication rejection; login forms stay minimized until explicit login. JSON errors include only fixed readback categories and optional numeric HTTP status. Typed adapter failures retain their categories with replacement messages, excluding raw browser errors. Fixed Linux/Chromium hints were removed from the legacy Node client because they contradicted the captured browser user agent; their contribution to live rejection was not established.

Independent IPC review reproduced and blocked a queued cancellation/deadline race before the dispatch handshake fix.
