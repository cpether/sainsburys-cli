### Response-cookie follow-up

Ordinary HTTP responses previously ignored Set-Cookie, while successful live read responses were observed replacing cached cookie values. That is a concrete source gap, not proof of the live 401 cause. The retained HTTP implementation now uses tough-cookie 6.0.2 for host-only/domain/path/Secure/expiry/prefix/public-suffix rules, Max-Age precedence, replacements and deletions. Managed cached requests serialize under the same profile lock as login/logout, reload the latest matching login generation and persist private cookie state before readback. Abort/deadline checks prevent queued requests from sending later, and a delayed response cannot cross logout or a newer login. No bearer/custom-token synthesis, automatic cached reauthentication or mutation retry was introduced.

The HTTP and auth agents independently reviewed the changes. Findings fixed include lost positive Max-Age expiry after serialization and an old in-memory response overwriting a replacement session. The outer basket signal tracker now distinguishes a queued unsent mutation from an actual unverified write; two real CLI signal regressions fail on the old tracker and pass with the fix. Twenty-three cookie regressions and a login-generation regression cover rotation/persistence/reload, scopes, TTL/deletion, concurrent processes, login/logout races, cancelled/late requests, private-save failure and no mutation replay. Typecheck, build, all 183 tests and dependency audit pass, with zero advisories. The new dependency was added through the lockfile after checking its current primary documentation and registry metadata.

A bounded read-only live check after the cookie fix passed fresh-process identity, context, empty basket and identity reuse. Updated cookies were persisted while the account identity and original login timestamp stayed unchanged. The fix's live mutation/readback path has not been re-tested and requires new approval. Sustained session reliability, the cause of the earlier rejection, natural expiry, booked-slot context and weighted products remain unverified. If the next bounded pilot still cannot sustain verification, explain that evidence before replacing the transport.

The undocumented API can change, bot protection may reject replay, and the profile/context schemas may require adjustments after sanitized live observation. A plan is not an atomic retailer transaction. Price changes or a readback failure can leave verified or uncertain partial changes. Weighted fulfillment, substitutions and later website actions prevent a local estimate from guaranteeing the eventual payment amount. Existing catchweight is preserved; new catchweight choices stay on the website. Removal still requires a resolvable product and valid price; otherwise use the website.

No diagnostics are retained: screenshots, HAR capture and browser-page dumps were removed. Private opt-in diagnostic capture would need a separate redaction/retention implementation before introduction. No SMS/chat bridge is supported. There is no automatic reauthentication loop and no payment/amendment/booking execution code.

The approval digest binds plan contents to a review, but does not authenticate a human or isolate the agent. A same-user shell-capable agent can read session state or alter this code. Strong enforcement requires credentials in a separately isolated account/service and an allowlisted interface with an approval channel outside agent control. Local logout cannot revoke copied tokens.
